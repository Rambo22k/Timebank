# Base de datos de TimeBank

Esta migración de la base de datos de Supabase constituye la base de datos en ingles para la propuesta de TimeBank. Crea el esquema de PostgreSQL, las restricciones, los índices, las políticas de seguridad a nivel de fila (RLS), los flujos de trabajo de créditos del lado del servidor y los buckets de Storage.

## Aplicar el esquema

1. En Windows, instala Supabase CLI con Scoop. Después ejecuta `scoop bucket add supabase https://github.com/supabase/scoop-bucket.git` y `scoop install supabase`. Verifica con `supabase --version`.
2. Desde la raíz del repositorio, inicializa la configuración con `supabase init`. La carpeta `supabase/migrations/` ya existe; la inicialización añade allí `supabase/config.toml`.
3. Inicia sesión con `supabase login` y vincula el proyecto hospedado con `supabase link --project-ref TU_PROJECT_REF`.
4. Aplica la migración con `supabase db push`.
5. En Supabase Auth, habilita el inicio de sesión mediante correo electrónico y contraseña, así como mediante Google. Configura las URL de redirección permitidas para la PWA y el enlace profundo de Capacitor, y exige la confirmación del correo electrónico.
   Para desarrollo web, añade `http://localhost:4200/auth/callback` y `http://localhost:4200/auth/update-password` a **Authentication → URL Configuration** y usa `http://localhost:4200` como Site URL. Añade las rutas equivalentes del dominio publicado antes de desplegar.
6. Después de crear la primera cuenta, asigna el rol de administrador de confianza desde el Editor SQL de Supabase:

   ```sql
   insert into public.user_roles (user_id, role)
   values ('YOUR_AUTH_USER_UUID', 'admin');
   ```

   Para los cambios posteriores de roles, utiliza `public.set_user_role(...)` para que queden registrados en el historial de auditoría.

## Contrato de integración de la aplicación

- El registro debe proporcionar `birth_date`, `accepted_terms_at` y `accepted_privacy_at` en los metadatos del usuario de Supabase Auth. Los usuarios también pueden actualizar sus campos privados del perfil después del registro. La edad mínima es de 18 años por defecto.
- La aplicación web configura `@supabase/supabase-js` con la URL del proyecto y una clave pública (`anon`/publishable) en `src/environments`. Nunca incluyas una clave `service_role`/secret en el cliente.
- La aplicación debe utilizar funciones RPC para las solicitudes de sesiones, la aceptación, la cancelación, la confirmación de sesiones, las disputas, las donaciones de créditos, las aprobaciones de solidaridad, los ajustes administrativos, los cambios de estado de las cuentas y las decisiones de verificación. Nunca debe modificar directamente los saldos ni los registros del libro mayor.
- Los usuarios pueden desactivar temporalmente su cuenta mediante `public.deactivate_my_account()` después de resolver las solicitudes y sesiones pendientes. La eliminación permanente de un usuario de Auth debe realizarse en el servidor mediante la API de administración de Supabase Auth, después de gestionar cualquier saldo de créditos restante.
- Las cantidades de créditos son valores numéricos, donde un crédito representa una hora. La duración de las sesiones debe utilizar incrementos de 15 minutos.
- Sube los avatares al bucket público `profile-avatars`, dentro de una carpeta de primer nivel cuyo nombre sea el UUID del usuario autenticado. Sube los documentos de identidad al bucket privado `identity-documents`, utilizando la misma convención de carpetas. Guarda la ruta del objeto resultante en `profiles.avatar_path` o `identity_verifications.document_path`.
- Las nuevas reuniones se crean con Google Meet al aceptar una solicitud. El proveedor conecta su propia cuenta Google desde **Mi perfil**; la reunión se crea bajo esa identidad, con moderación activada y acceso restringido. La otra persona entra como participante y puede tener que pedir acceso al anfitrión. La URL solo se muestra a los participantes y a administración mediante RLS. Las sesiones aceptadas antes de la migración conservan su enlace actual; cancela y vuelve a coordinar una sesión para crearla en Google Meet.
- La migración `20261110100000_google_meet_hosted_sessions.sql` sustituye la aceptación anterior y rechaza enlaces que no correspondan a una sala Meet creada para esa solicitud por la cuenta del proveedor. La función `create-google-meet-session` serializa solicitudes concurrentes, reserva créditos una sola vez y conserva/reutiliza la sala si falla la respuesta final.
- Para habilitar Google Meet, en Google Cloud activa **Google Meet REST API**, configura la pantalla de consentimiento OAuth y crea un cliente OAuth de tipo **Web application** separado del proveedor de Google que ya usa Supabase Auth. Registra como URI de redirección autorizada `https://arwywjsqgvnkeuwjcnpo.supabase.co/functions/v1/google-meet-oauth`. La app solicita el scope sensible `https://www.googleapis.com/auth/meetings.space.created`; mientras esté en modo de prueba, añade las cuentas de Google de los proveedores como usuarios de prueba. La publicación pública puede requerir verificación de Google. Los refresh tokens de una app externa en modo **Testing** vencen a los 7 días, así que cada anfitrión de prueba tendrá que reconectar; para uso general, publica y completa la verificación OAuth que Google solicite.
- En **Supabase → Edge Functions → Secrets**, guarda `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_TOKEN_ENCRYPTION_KEY` y `TIMEBANK_SITE_URL`. El último debe ser el origen web de la aplicación (`http://localhost:4200` para desarrollo local o el dominio publicado). `GOOGLE_TOKEN_ENCRYPTION_KEY` debe ser Base64 de 32 bytes aleatorios. Los refresh tokens se cifran en el servidor con AES-GCM. Nunca pongas estos secretos en Angular ni en el repositorio. Despliega con `supabase functions deploy google-meet-oauth` y `supabase functions deploy create-google-meet-session`.
- La migración `20261110090000_admin_permanent_user_deletion.sql` añade la eliminación permanente de miembros desde administración. Antes de borrar el Auth user, anonimiza el perfil, retira contenido identificable y limpia sus fotos/documentos privados. Conserva el historial financiero y de sesiones como registros auditables; exige saldo cero y ningún intercambio abierto. Despliega `supabase functions deploy admin-delete-user` para procesar el borrado de Auth y Storage desde el servidor.
- Se puede habilitar Realtime para `messages` y `notifications` en la publicación Realtime de Supabase. Las políticas de la base de datos siguen aplicándose a las suscripciones.
- La migración `20261104230000_schedule_timebank_maintenance.sql` habilita `pg_cron` y programa `public.expire_session_requests()` cada hora y `public.mark_unconfirmed_sessions_disputed()` en el minuto 15 de cada hora. Revisa su historial en **Integrations → Cron → Jobs**; los horarios se interpretan en UTC.
- Utiliza los flujos integrados de confirmación de correo electrónico y recuperación de contraseñas de Supabase Auth. El SMTP integrado de Supabase solo envía correos de Auth; los correos RF-60 de eventos de TimeBank se registran en `email_outbox` y se entregan desde `dispatch-email-outbox` mediante la API de Resend. La función solo incluye solicitudes, cambios importantes de intercambio, sesiones, créditos, reseñas, verificación, solidaridad y reportes; los mensajes del chat siguen siendo notificaciones dentro de la app.
- Para habilitar la entrega RF-60, necesitas una cuenta Resend con remitente verificado. No coloques `RESEND_API_KEY` en Angular ni en el repositorio. Despliega la función con `supabase functions deploy dispatch-email-outbox` y configura estos secretos en el entorno de Supabase: `RESEND_API_KEY`, `TIMEBANK_EMAIL_FROM`, `TIMEBANK_SITE_URL` y `EMAIL_DISPATCH_SECRET`. `SUPABASE_URL` y `SUPABASE_SECRET_KEYS` los proporciona el entorno Edge de Supabase (`SUPABASE_SERVICE_ROLE_KEY` queda como compatibilidad con la clave heredada). Los correos solo se envían a cuentas con el email confirmado.
- `dispatch-email-outbox` debe ser invocada de forma programada para reintentar envíos pendientes; habilita `pg_net` si aún no está activo y crea un trabajo de Supabase Cron que invoque `https://<project-ref>.supabase.co/functions/v1/dispatch-email-outbox` cada minuto. Guarda la URL del proyecto y el mismo `EMAIL_DISPATCH_SECRET` en Supabase Vault, y envía el secreto en `Authorization: Bearer <secret>`. La función reclama filas con bloqueo, evita duplicados con una clave idempotente de Resend y reintenta fallos con espera progresiva.
- La migración `20261108100000_member_contacts.sql` añade la búsqueda autenticada de miembros y las solicitudes de contacto. Aplícala con `supabase db push`; los perfiles consultados exponen solo campos públicos y las relaciones solo se modifican mediante RPC.
- La migración `20261108120000_replace_pending_identity_document.sql` permite reemplazar una identificación mientras sigue pendiente, sin conceder al cliente permiso para editar la decisión ni otros campos de la revisión.
- La migración `20261108140000_weekly_availability_workflow.sql` agrega las RPC seguras para registrar y quitar franjas semanales, valida zona horaria e impide solapamientos del mismo día.
- La migración `20261108160000_teaching_offers_and_request_origins.sql` permite ofrecer una habilidad a una persona que la busca y registra quién inició cada intercambio para que ambas direcciones compartan la misma reserva de créditos y sesiones.
- La migración `20261108180000_profile_country_languages_and_locales.sql` guarda país, zona horaria, idiomas hablados e idioma preferido de la interfaz. También añade el RPC `public.update_my_profile_settings(...)` para guardar el perfil y reemplaza el alta automática para conservar país y zona horaria del registro. Explorar usa país e idiomas hablados como filtros.
- La migración `20261108200000_language_preference_rpc.sql` cambia el idioma de la cuenta sin exigir que un perfil antiguo haya completado primero los campos de país y zona horaria.
- La migración `20261108210000_remove_dark_theme.sql` retira la preferencia de tema y su RPC, y restaura el alta de usuarios sin esa configuración.
- La migración `20261108220000_direct_solidarity_donations.sql` permite que una persona consienta publicar un resumen breve de su solicitud para recibir donaciones dirigidas. Los motivos privados nunca se exponen; las donaciones siguen entrando al fondo compartido y la asignación depende de la aprobación administrativa. También habilita la vista de la Red de Tiempo desde las sesiones completadas del usuario.

## Módulos incluidos

Perfiles y roles, idiomas, categorías, habilidades ofrecidas y solicitadas, disponibilidad recurrente, solicitudes de sesiones y sesiones, prevención de solapamientos, cuentas de monedero, historial inmutable de transacciones y del libro mayor, reseñas y reputación, verificación de identidad, solicitudes de solidaridad y donaciones, chat privado, bloqueos de usuarios, reportes, notificaciones dentro de la aplicación, tokens de dispositivos para notificaciones push, historial de auditoría, indicadores de abuso, configuración de la aplicación, resumen público del fondo de solidaridad y políticas de Storage.

La migración `20261102000000_timebank_demo_and_skill_fields.sql` ajusta el crédito de bienvenida a 5 y agrega a `skills` los campos de modalidad, etiquetas, nota de disponibilidad, ubicación y destacado que utiliza la interfaz. Si la migración anterior ya se aplicó al proyecto remoto, ejecuta `supabase db push` para aplicar este cambio incremental.

## Consideraciones de seguridad

- Los perfiles exponen únicamente los campos públicos. La fecha de nacimiento, la aceptación de políticas y el estado de la cuenta se almacenan en `profile_private`.
- Todas las tablas de la aplicación tienen habilitada la seguridad a nivel de fila (RLS). Los usuarios anónimos solo pueden consultar las habilidades activas y los perfiles públicos.
- Los saldos de los monederos solo pueden modificarse dentro de funciones del lado del servidor. Los registros del libro mayor no pueden actualizarse ni eliminarse; al borrar una cuenta, un administrador solo puede anonimizar la descripción libre de las transacciones, sin cambiar montos ni saldos.
- Los documentos de identidad se almacenan en un bucket privado de Storage. Solo su propietario y los administradores pueden leerlos.
- Asigna roles de administrador únicamente a cuentas de confianza. La asignación inicial del rol se realiza desde el Editor SQL; los cambios posteriores deben efectuarse mediante la función RPC auditada.
